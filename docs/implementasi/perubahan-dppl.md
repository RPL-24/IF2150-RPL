# Perubahan Implementasi terhadap DPPL

Catat setiap bagian implementasi yang berbeda dari DPPL (`docs/M8/K03_G07_DPPL2.md`). Dipakai untuk laporan B.1.

| No | Bagian DPPL | Rancangan di DPPL | Implementasi | Alasan | PIC |
|---|---|---|---|---|---|
| 1 | C03 Lokasi | Tidak ada operasi `dalamWilayah()` | Operasi baru `Lokasi.dalamWilayah()`: cek titik di dalam polygon batas Kota Bandung (`src/lib/batas-wilayah.ts`, dari OpenStreetMap via Nominatim, disederhanakan ±300 m) dengan algoritma ray casting | Dibutuhkan untuk validasi "Lokasi di luar daerah penanganan" (I01-13) dan validasi koordinat data seed | F (Dipta) |
| 2 | Controller (C17–C23) | Tidak ada controller autentikasi; UC01–UC06 tidak mencakup masuk/daftar/keluar | Controller baru `AuthController` (`src/server/controllers/AuthController.ts`) dengan operasi `masuk()`, `daftar()`, `keluar()` memakai Supabase Auth email + password; validasi input di `src/lib/validasi-auth.ts`. Akun baru selalu ber-role `warga` | Dibutuhkan agar sistem bisa membedakan aktor (Warga, Tim Administrasi, Eksekutor Lapangan) dan membatasi akses halaman serta aksi per aktor | F (Dipta) |
| 3 | Bab 6 I02-06 / I02-11 (warna status) | Warna hanya disebut untuk Diterima (biru), Dikerjakan (kuning), Berhasil (hijau) | `STATUS_WARNA` di `src/lib/constants.ts` menambah warna merah untuk status Ditolak | I02-06 meminta warna berbeda untuk setiap status, tetapi warna Ditolak tidak disebut | F (Dipta) |
| 4 | C02 Laporan (tahap penanganan) | Tidak ada label tahap penanganan | `TAHAP_LABEL` di `src/lib/constants.ts`: "Menunggu eksekusi", "Menunggu evaluasi" | Kolom `tahap` ada di skema untuk membedakan sub-tahap status Dikerjakan; labelnya diturunkan dari nama enum karena tidak disebut di DPPL | F (Dipta) |
| 5 | C17/C20/C21/C23 (pemanggilan `NotifikasiController.kirimNotifikasi`), C02 `updateStatus`, C06 `hitungPrioritas` | Controller memanggil `kirimNotifikasi()` dan mencatat riwayat status setelah menyimpan data; pesan tanpa ID tiket; notifikasi eksekutor hanya untuk "Belum Selesai"/"Minta Ulang Bukti" | Trigger DB di migration `20261107155512_trigger_status.sql`: `cek_transisi_status` (state machine), `catat_perubahan_status` (riwayat + notifikasi pelapor di setiap perubahan status/tahap), `tambah_upvote` (counter + skor `least(100, upvote × 10)`), `terima_hasil_perbaikan`, `terapkan_evaluasi` (notifikasi eksekutor untuk semua keputusan, termasuk "selesai"). Teks DPPL dipakai dengan tambahan ID tiket, mis. "Laporan Anda (LK-0001) telah divalidasi dan diteruskan ke tim lapangan." | Atomik (status, riwayat, dan notifikasi tersimpan dalam satu transaksi) dan tidak bisa dilewati walau Server Action dipanggil langsung; ID tiket diperlukan karena satu warga bisa punya banyak laporan | F (Dipta) |
| 6 | C04 Foto / C05 Video (atribut `url`), Q-002/Q-003 | Atribut `url` disimpan di tabel; bucket tidak dirinci | Bucket Storage `media` **public** (migration `20261107162818_storage_media.sql`), tabel menyimpan `path` (bukan URL penuh); URL dibentuk `Foto.urlMedia(path)`. Upload hanya lewat policy INSERT ke `{laporan\|hasil}/{user_id}/{uuid}.{ext}` (laporan → warga, hasil → eksekutor); tidak ada policy SELECT/UPDATE/DELETE | URL publik bisa langsung dipakai di `<img>`/`<video>` dan peta publik (KF20) tanpa signed URL yang kedaluwarsa. Trade-off: siapa pun yang tahu path bisa membuka berkas, termasuk bukti laporan yang ditolak; risiko kecil karena path memakai UUID acak dan tidak bisa di-list. | F (Dipta) |
| 7 | C04 `isFotoValid()` / C05 `isVideoValid()` (Algo-009/010) | Operasi tanpa parameter pada objek; hanya cek format dan `ukuran > 10 MB` | Fungsi `isFotoValid(berkas)` / `isVideoValid(berkas)` menerima `{name, size}` (mis. `File`); format dari ekstensi (`.jpeg` → `jpg`, tidak peka huruf besar), ukuran 0 juga ditolak. Operasi tambahan: `formatDariNama()`, `urlMedia()` | Entity berupa kumpulan fungsi (AGENTS.md); MIME dari browser sering kosong untuk .mkv sehingga ekstensi lebih andal; tabel punya CHECK `ukuran > 0` | F (Dipta) |
| 8 | Bab 6 I01-05..10, I06-05..07 (File Upload) | Satu foto dan satu video per formulir di mockup; batas jumlah berkas tidak disebut | Komponen `MediaUploader` (shared), satu instance per field (foto / video), batas jumlah lewat prop `maks` (default 3, **usulan**). Pesan error berkas memakai teks Algo-019 "Foto harus JPG/PNG, video MP4/MOV/MKV, maks. 10 MB" | Q-002/Q-003 memakai `List[Foto]`/`List[Video]`, jadi lebih dari satu berkas dimungkinkan | F (Dipta) |
| 9 | C10 Notifikasi / C23 NotifikasiController | Tidak merinci mekanisme notifikasi in-app | Tabel `notifikasi` ditambahkan ke publication `supabase_realtime`; client subscribe `postgres_changes` (tersaring RLS milik sendiri) | Notifikasi tampil tanpa reload halaman | F (Dipta) |
| 10 | C02 `simpanLaporan()` (Algo-002), C08 `simpanBukti()` (Algo-015), Q-001..Q-004 | Insert laporan/hasil perbaikan lalu insert foto/video satu per satu dari aplikasi | Satu RPC Postgres per operasi (migration `20261107162818_storage_media.sql`): `kirim_laporan(p_kategori, p_deskripsi, p_latitude, p_longitude, p_media)` → `(id, id_tiket)` dan `kirim_hasil_perbaikan(p_id_laporan, p_catatan, p_media)` → `id_hasil`. `p_media` = array `{path, format, ukuran, tipe}`. `SECURITY INVOKER`, jadi grant kolom, RLS, dan trigger tetap berlaku. `Laporan.simpanLaporan()` memanggil `kirim_laporan`; laporan wajib ≥ 1 foto/video, hasil perbaikan wajib ≥ 1 foto (I06-08) | Atomik: kalau satu baris media ditolak, laporan/hasil perbaikan ikut batal, sehingga tidak ada laporan tanpa bukti. Supabase JS tidak punya transaksi multi-request | F (Dipta) |
| 11 | C04 Foto / C05 Video (tabel `foto`, `video`) | Tidak ada aturan isi `url` | Policy RESTRICTIVE insert pada `foto` dan `video`: folder pertama `path` = `laporan` (jika `id_laporan` terisi) atau `hasil` (jika `id_hasil` terisi), folder kedua = `auth.uid()`, dan ekstensi `path` = kolom `format` | Baris media tidak bisa menunjuk berkas milik user lain atau folder yang salah, walau Server Action/RPC dipanggil langsung | F (Dipta) |
